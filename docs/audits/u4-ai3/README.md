## 2. 切片 A：`ai_usage` 用量台账（`f7c46e3`）

### 2.1 表结构（迁移 `0003`，drizzle-kit 生成；业务表 12 → 13）

| 列 | 说明 |
|---|---|
| `id` / `created_at` | 主键与时间（有两个索引：时间、动作） |
| `action` / `scene` | 写作动作（可空：自由对话/ping）／场景（`chat`/`ping`） |
| `profile_id` / `model` | 档案快照（配置被改后仍可追溯当时用的是哪个） |
| `prompt_tokens` / `completion_tokens` / `total_tokens` | **可空**，见 §2.2② |
| `duration_ms` | 完整流耗时 |
| `status` / `error_code` | 三态 + 结构化码，见 §2.2①③ |

### 2.2 三条口径决定（逐条有理由，且都有单测）

**① `aborted` 与 `error` 分开，不算失败。**
用户主动停止、客户端断连（换页/关标签）都不是服务故障。计入错误率会让统计**随用户操作习惯失真**
（活跃用户看起来「错误率更高」）。⇒ 三态 `ok`/`error`/`aborted`，`successRate` 分母只含 `ok + error`；
分母为 0 时返回 **`null`**（「无样本」与「成功率为零」是两件事）。

**② token 可空，`null ≠ 0`。**
上游不保证每个响应都给 usage（`ping` 出于安全考虑根本不读响应体）。拿不到时写 `null`（未知），
**不写 0** —— 0 表示「确实零消耗」，两者对求平均、算费用的意义完全不同。
聚合另暴露 `tokenSamples`（有 token 的调用数）让调用方知道样本量。

**③ 错误只存结构化码，不存上游原文。**
上游错误体可能含内部 URL / key 片段（`ai-chat.service` 的 `ping` 特意不读错误 body 就是同一考虑）。

### 2.3 接线

`AiChatService` 注入 `AiUsageService`（**值导入** —— DI 依赖运行时元数据），在 `ping` 与 `stream` 两个出口记账。

`stream` 用**可变收集器**而非返回值：`pump` 在异常路径下不返回，而异常时同样要记账 ——
只有共享可变状态能覆盖全部出口（成功 / 首字节后中断 / 首字节前失败 / 客户端断连）。

**写入纪律：旁路，绝不阻断主业务。** `record()` 内部全 `try/catch`，失败只 `warn`。
用户来润色文章，不该因为「记账失败」而拿不到结果（台账不能成为单点故障）。
单测用「DB 已关闭」构造真实失败路径并断言不抛。

保留策略：行数上限 `AI_USAGE_KEEP = 5000`，超出后**批量**删最旧（非逐行）。

端点：`GET /admin/ai/usage?days=N`（缺省 7，上限 365）→ `totals` + `byAction` + `recent` +
`retainedRows` + `keepLimit`。**聚合在 SQL 里做**，不随台账行数线性变慢。

## 3. 切片 B：`meta` 结构化契约与非破坏性回填（`f7c46e3` + `b990148`）

### 3.1 解析器放 L0 而非服务端

`meta` 走的是**流式**通道（与其他动作同一条 SSE），文本在浏览器里逐帧累积。
若解析只在服务端做，就得为它单开一条非流式端点 —— 那会同时带来
「同一动作两套实现」与「前端还得再拼一次」两个问题。
⇒ `packages/shared/src/ai-meta.ts`，两端共用同一份解析与回填规则，且**可被单测直接覆盖**。

### 3.2 核心铁律：绝不静默覆盖用户已写内容

用户可能已经手写了标题、摘要与标签，此时「一键生成」若直接写入就是**摧毁用户劳动**。
三层共同保证：

| 层 | 机制 |
|---|---|
| ① `planMetaBackfill()`（纯函数） | 算出四态：`fill`（原为空，可安全填）/ `conflict`（原非空且不同，须确认）/ `same` / `empty`（本次无建议，**不动**现有内容） |
| ② 界面 | `conflict` 项**默认不勾选**，文案显式写「将覆盖你已写的内容 —— 请确认」，并用删除线 + 箭头展示「原值 → 新值」差异 |
| ③ `apply(patch)` | **只提交被勾选的键** —— 未勾选字段一个字节都不动（不是「部分更新」，是「只改这些」） |

把判定做成**纯函数**是关键：它不依赖界面，也就不可能被界面改坏；单测里有专门用例断言
「非空且不同时绝不产生 `fill`」。

回填后**仅改前端响应式状态**，用户显式点保存才落盘（提示语明说这一点）。

新增 `apps/web/src/lib/ai/backfill.ts`：沿用既有 `lib/ai/context.ts` 的注册模式
（聊天栏挂 `MainLayout`、编辑页在 `router-view` 深处，两者非父子；注销时只有
「自己仍是当前」才清空，防快速切换编辑页的竞态）。

### 3.3 解析容错立场

模型输出**不是**可靠的结构化数据。上游可能：行首加「第一行：」标签、用 Markdown 粗体包裹、
多出空行、少给标签行。解析器一律**尽力而为**，且**完全解析不出时返回全 `null` 而不抛错**
（调用方据此提示「未能识别，请重试」，而不是把整段原文塞进标题）。

**不做「按关键词猜哪行是标题」这类花活**：提示词明确要求了行序，按序取比按内容猜更稳也更好解释。

### 3.4 发布前检查清单

`packages/shared/src/publish-check.ts`（纯函数），编辑器页接入。

| 级别 | 项 | 行为 |
|---|---|---|
| `error` | 标题为空 / 正文为空 / （Shirone）缺发布日期 | **阻止发布** |
| `warning` | 缺摘要 / 缺标签 / 摘要过长 / 正文过短 | 只提示 |
| `info` | 分类未设 / （Mizuki）未设发布日期 | 仅告知 |

**关键产品语义：只有 `error` 阻止发布。** 把 warning 也做成阻止项，会让用户为了发一篇文章
被迫编造摘要与标签 —— 那是坏产品。

**检查项按主题能力分化**而非按档位名写死：Shirone 的构建期 schema 把 `published` 定为必填
（缺它 `astro build` 直接 `throw InvalidContentEntryDataError`），故
`requirePublished: isShironeTheme` ⇒ Shirone 下缺发布日期是 `error`，Mizuki 下只是 `info`。
与后端 `capabilities` 保持同一口径。

清单**已通过项也展示** —— 让用户知道系统确实检查了这一项，而不是只看到一堆红字。

### 3.5 用量面板

AI 设置页新增**折叠区**（旁路信息，不打断配置主任务）：totals 摘要 + 按动作分组表 +
窗口选择（1/7/30/90 天）。

**口径不在前端重算**：`successRate` 由服务端给出且分母不含 `aborted`。前端只展示，
避免两处口径漂移。表格对「部分调用未返回 token」显式标注 `（n/m 有计数）` ——
`tokens` 只是**已知样本之和**，不是全部消耗，混在一起会误导。
用量拉取失败只 `warn`，不打断配置页。
